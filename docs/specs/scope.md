# Cept scope: phases and deferrals

**Status:** Owner answers recorded 2026-10-07 (decisions D-26 to D-40) · **Owner:** nsheaps · **Source:** [requirements](requirements/README.md)

This page records which requirements the current build-out (Phase 1) covers, which wait for Phase 2 or 3, which are deferred without a phase, and which are out of scope. The decisions behind it are D-26 to D-40 in [requirements §6](requirements/README.md#6-conflicts-and-owner-decisions-needed); the area files carry a scope note under each affected requirement.

## Owner's scope statement

> Build Cept up to, but not including, live co-editing, CLI tools and daemons, the VS Code plugin, and databases. That means full space functionality, syncing with a remote on GitHub, comments, full Markdown file support with front matter for metadata, native app distribution bundles, the PWA, Pulumi setup for Cloudflare in nsheaps/iac for the GitHub App login (while also supporting PATs), and autodiscovery of spaces based on what the login has access to.

The owner's answers then narrowed this: Phase 1 signs in with **PATs only**; the GitHub App, the login relay Worker and all nsheaps/iac work move to Phase 2 (iac is being restructured first); databases and static rendering are Phase 2; native-app login callbacks are Phase 3; Notion import and `[[wiki-links]]` are out.

## 2. Phase decisions

- D-26 Phasing. Phase 1 = this build-out (everything in scope except below). Phase 2 = databases (REQ-EDT-006..009, D-16), static rendering / SSG / docs site (all REQ-SSG, REQ-WEB-017, REQ-WEB-018 bundled-docs generation, REQ-CLI-011, REQ-ENG-016, REQ-NTN-009 comments in static views), GitHub App login + OAuth relay Worker + all nsheaps/iac Pulumi/Cloudflare work (iac will be restructured first). Phase 3 = native-app login callbacks / deep links for OAuth. "later" = co-editing (REQ-COL), CLI/daemon (REQ-CLI except CLI-011 which is phase 2), VS Code (REQ-VSC), Google Drive + SFTP backends and logins (REQ-WS-015/016, REQ-AUTH-006/007), templates (NTN-014), synced blocks (NTN-015), @person mentions, app-store submissions, opening PRs from the app, nested spaces (WS-005/006), comment threading and resolving. "out" = Notion import (NTN-017), [[wiki-links]] (EDT-017), custom domains / nsheaps.dev (SSG-011 is phase 2 with SSG only if it is about published sites; the app itself stays on GitHub Pages).
- D-27 Auth in Phase 1 is PATs only (fine-grained recommended, classic accepted). GitHub App login, the relay Worker (when built: a Worker just for Cept), auth.nsheaps.dev, the GitHub App registration and all Pulumi/iac work are Phase 2. Production app = GitHub Pages (nsheaps.github.io/cept/app) + PWA; no custom domain.
- D-28 Native distribution. Desktop: macOS dmg (arm64+x64), Windows NSIS x64, Linux AppImage + deb x64; Electrobun updater fed from GitHub Releases. Android APK in Phase 1, but it is not done until release signing/publishing secrets exist. iOS builds in CI (simulator); distribution waits for an Apple Developer account. Distribution channel = GitHub Releases only; signing optional with ::warning:: when secrets are missing; store submissions later.
- D-29 Storage & hosts. Phase 1 backends: browser IndexedDB, desktop local folder, File System Access API folders on web (REQ-WS-012), GitHub. Host = GitHub only (PAT); anonymous read-only clone of public HTTPS git URLs keeps working; AuthProvider stays host-agnostic. Backend switching (REQ-WS-020) limited to "publish a local/browser space to a new GitHub repo".
- D-30 Spaces, autodiscovery & branches. In: multiple spaces per repo, lifecycle (create, rename, remove-from-device, delete), legacy flat-space migration, .git detection (REQ-WS-021). Autodiscovery: every repo the PAT reaches (GET /user/repos), default branch scanned via Git Trees API, forks and archived repos skipped, found spaces listed as "Discovered" and cloned only when opened or pinned. space.cept.yaml MAY declare `branch: <name>`; the marker file MUST exist on the default branch (that is where discovery finds it), and Cept then uses the declared branch for that space. This extends the D-3 minimal schema (name, slug, version) with optional `branch`. Rejected push falls back to "push to a new branch". Opening PRs from the app is later.
- D-31 Page history is provided by the storage backend (git history for GitHub-backed spaces). History list, diff and restore are Phase 1, exposed via backend capabilities; backends without history hide the UI.
- D-32 Links & graph. Crosslinks use standard GFM links `[text](relative/path.md)` only; [[wiki-links]] are out (REQ-EDT-017 out). Backlinks and search are Phase 1, derived from standard links. Graph builder/model/view (REQ-EDT-018..020) are Phase 1; the graph view may be delivered as a fenced ```graph block plugin.
- D-33 Markdown. GFM incl. footnotes, math, lossless round-trip and one pipeline (D-14, D-15) are Phase 1. Mermaid must render as on GitHub and is the first fenced-block plugin; ```graph may be the second. An internal plugin interface for fenced-block plugins is Phase 1 (REQ-EDT-013 moves to Phase 1 for the internal interface; a third-party plugin registry is later).
- D-34 Comments are stored inline in the page as structured HTML comments, e.g. `<!-- cept:comment {"id":...,"author":...,"created":...,"anchor":...,"body":"markdown"} -->` (exact format to be specified), not in a sidecar file. Author = signed-in GitHub identity (from the PAT's user). Threading and resolving are later, but the structure leaves room for them; a later version may reference a separate file. Notifications: in-app "new since last visit" badge only.
- D-35 Notion parity. Phase 1: move/reorder (front-matter `order`), icon/cover in front matter (NTN-013), page history (NTN-016, see D-31), @page and @date mentions (EDT-004 partially; @person later). Templates and synced blocks later. Notion import out.
- D-36 Databases are Phase 2. In Phase 1, database entries are removed from the slash menu/UI so nothing half-working ships; library code is left untouched.
- D-37 D-4/D-5 approved as stated: full offline editing with queued commits and push-on-reconnect in Phase 1.
- D-38 Engineering prerequisites (fix CI, mise tasks, secret scanner) are Phase 1; other REQ-ENG items only as needed.
- D-39 Phase 1 browser git transport: keep the public `cors.isomorphic-git.org` proxy behind one build-time setting (never hardcoded in components); the first-party Worker replaces it in Phase 2. Temporarily relaxes D-9; the public proxy sees users' PATs.
- D-40 Desktop OS integration: no tray icon; native app menus are Phase 1 as another route to About, Help and Settings; deep links are Phase 3.

## 10. nsheaps/iac findings (Phase 2)

### 10.1 What exists today

I looked through nsheaps/iac at /home/user/iac without changing anything. Pulumi is already set up there with two projects, and one of them (`cloudflare-apps`) is a Cloudflare stack written for Cept: it has a `cept.nsheaps.dev` DNS record, a Worker named `nsheaps-cors-proxy` whose allowed origins include Cept, and an `auth.nsheaps.dev` hostname. Nothing in that stack works yet:

1. **No working deploy.** Its only deploy run on 2026-03-05 failed (logs have expired, so the cause is unknown). Every manual step in `cloudflare-apps/TASKS.md` is still unchecked, and both preview workflows are switched off with `if: ${{ false }}`.
2. **The code is written for an older provider version.** `index.ts` uses the v5-style API, but `@pulumi/cloudflare` is pinned at ~6.21.0. I unpacked 6.21.0 and confirmed the mismatch:
   - `WorkersScript` now requires `scriptName` and takes `bindings: [{type: 'plain_text', ...}]`; `name`, `module` and `plainTextBindings` no longer exist.
   - `Zone` now needs `account: {id}` and `name`, not `zone`.
   - `cloudflare.Record` is deprecated in favour of `DnsRecord`.
   - So the stack most likely fails type-checking and `pulumi up` as written.
3. **The Worker only ever ships a placeholder.** Its code comes from the `CORS_PROXY_SCRIPT` env var, and CI never sets it, so every deploy uploads a stub that returns 503.
4. **`auth.nsheaps.dev` probably doesn't reach the Worker.** It is a CNAME to `nsheaps-cors-proxy.workers.dev`, but workers.dev hostnames include an account subdomain, so that target is likely wrong. There is no `WorkersCustomDomain` or `WorkersRoute` resource.
5. **CI installs with the wrong package manager.** CI runs `yarn --cwd cloudflare-apps install --immutable`, but that folder has a `package-lock.json` and no `yarn.lock`, and the root `package.json` declares no workspaces.
6. **Pulumi state isn't set up for CI.** CI sets neither `PULUMI_BACKEND_URL` nor `PULUMI_ACCESS_TOKEN`. The wrapper script falls back to local `file://` state, which wouldn't survive between CI runs. The plan to store state in R2 has a chicken-and-egg problem: the R2 state bucket is created by the same stack whose state would live in it.
7. **No GitHub token-exchange relay exists.** iac has no code for the GitHub login token exchange. The Worker's real code was meant to come from a separate repo, nsheaps/cors-proxy. This session can't reach that repo through the GitHub API (it returned 403), so its contents are unknown.

Cept's own spec already asks for this Worker. `docs/specs/requirements/09-remotes-and-auth.md` (REQ-AUTH-003/008/009) says one Worker provisioned through iac should handle the GitHub token exchange and refresh plus Git push/pull traffic, with an origin allowlist and no stored state. It lists most of these iac defects too, and it has 10 open questions (§"Conflicts and open questions"). Cept today has no login code wired into the UI; its GitHub provider talks to github.com directly (which browsers block) and the app hardcodes the public proxy `cors.isomorphic-git.org`.

The sibling project github2 has the closest existing example (`relay/relay.worker.js`, about 50 lines). It is a stateless, secret-free Worker that only accepts POSTs, forwards to a short allowlist of github.com login endpoints passed as `?url=`, and adds CORS headers (it allows any origin). The PKCE login code in `src/api/oauth.js` could be ported to Cept almost as-is. But github2's relay was never actually deployed: in production `src/config.js` sets `AUTH_RELAY = 'https://api.cors.lol/'`, a public third-party proxy that sees users' login codes and tokens. Its `PUBLIC_CLIENT_ID = '3946485'` also looks like an App ID rather than a client ID (those usually start with `Iv`), which is worth checking.

Recommendation: take github2's idea but don't copy the file. Build one hardened, shared, first-party Worker in iac and serve Cept from it (github2 and private-pages could move to it later). It should check origins, use fixed routes instead of an open `?url=` parameter, carry Git push/pull traffic, optionally add a client secret on the server side, and never log tokens.

The GitHub App itself can't be created with Pulumi; `github-org/README.md` says the same. It has to be registered by hand or with a manifest script. Pulumi can only manage which repos an installation can reach.

Finding the user's spaces doesn't need the relay. api.github.com sends CORS headers, so Cept can list installations and their repos directly (or the user's repos with a PAT), then check each repo for `space.cept.yaml`.

### 10.3 Existing GitHub App and OAuth infrastructure

**iac**

- No relay for the GitHub login token exchange exists, and the only Worker deploys a 503 stub.
- `cloudflare-apps/TASKS.md` mentions updating "GitHub OAuth App redirect URLs" for private-pages and cept, which suggests an OAuth App already exists somewhere for private-pages. It isn't in the repo.
- `github-org/Pulumi.yaml` manages repos, branch protection and teams. It has a commented-out `github:AppInstallationRepository` for the automation app, and its README notes that GitHub Apps themselves can't be managed by Pulumi.
- The org's other app, automation-nsheaps (actor 2549081), is used for CI and repo settings only, not for user login.
- The real Worker code was meant to come from nsheaps/cors-proxy, which this session can't reach through the GitHub API (403), so its contents are unknown.

**github2 precedent** (`relay/relay.worker.js`, `src/api/oauth.js`, `docs/specs/auth.md`, skills `auth-relay` and `pkce-login`)

- The relay is a stateless Cloudflare Worker deployed by hand with `wrangler deploy`.
- It holds no secrets and only accepts POSTs.
- The target comes from a `?url=` parameter and must be one of `github.com/login/oauth/access_token` or `github.com/login/device/code`.
- It sends `Access-Control-Allow-Origin: *`.
- The client side handles login (PKCE S256 with Web Crypto, `state` in sessionStorage, redirect to `/callback`), refresh using the refresh_token, and device flow, all through the relay. A PAT login and an "app private key in the browser" login go straight to api.github.com.

Problems with it as precedent:

- github2's production config points `AUTH_RELAY` at the public third-party proxy `https://api.cors.lol/`, so a third party sees login codes and tokens.
- `PUBLIC_CLIENT_ID = '3946485'` looks like an App ID rather than a client ID (client IDs usually start with `Iv`).
- Its spec assumes GitHub's "SPA client" preview (github/roadmap #1153) allows a secret-free, CORS-enabled token exchange. That is unverified and may not apply to every app, so the relay may need to add `client_secret` itself.

**Can Cept reuse it?**

- Reuse the client-side PKCE and refresh logic (port it to TypeScript in `@cept/core`, using its own `TokenStore`) and the relay idea.
- Don't reuse the Worker file as-is. It allows any origin, has no git push/pull proxy, has no optional server-side secret, and has no tests or IaC.
- Build one shared, hardened first-party Worker in iac instead. github2 and private-pages could later move onto it, which would also get github2 off cors.lol.

**Cept today**

- `packages/core/src/auth/github.ts` is an OAuth-App-style provider that POSTs straight to github.com (blocked by CORS in a browser) and can send `clientSecret`.
- It has no PKCE, and no UI uses it.
- `App.tsx` hardcodes `cors.isomorphic-git.org`.
- `docs/specs/requirements/09-remotes-and-auth.md` REQ-AUTH-002/003/008/009/015/016 already specify the target design.

### 10.4 Proposed layout for Cept login

Keep the existing TypeScript project `cloudflare-apps/` (it already owns `cept.nsheaps.dev` and the Worker with Cept's allowed origins). Fix it and add a proper relay.

1. **Bootstrap / state.** Either move the R2 state bucket into a tiny `cloudflare-bootstrap/` project that uses local state checked in encrypted or kept in 1Password, or use Pulumi Cloud. Then set `PULUMI_BACKEND_URL` to R2 in every workflow and `.env.op`, so CI has durable state.
2. **Port `index.ts` to the v6 API** and split it into modules:
   - `cloudflare-apps/src/dns.ts`: `Zone` (`account`, `name`) and `DnsRecord` for `cept` and `private-pages`.
   - `cloudflare-apps/src/oauth-relay.ts`: a `ComponentResource` named `OAuthRelay`:
     - a `WorkersScript` with `scriptName`, ESM code and `mainModule`, and `bindings` for `plain_text` `ALLOWED_ORIGINS`, `ALLOWED_CLIENT_IDS` and `GIT_ALLOWED_HOSTS=github.com`, plus optional `secret_text` `GITHUB_CLIENT_SECRET_<id>` from `pulumi config --secret` or 1Password
     - a `WorkersCustomDomain` for `hostname auth.nsheaps.dev`, replacing the broken CNAME, or a dedicated `cept-auth.nsheaps.dev`
     - outputs: relay URL and client ID
3. **Worker source lives in iac** at `cloudflare-apps/workers/oauth-relay/`: `src/index.ts`, vitest unit tests with miniflare/workerd, and an esbuild bundle. Pulumi reads the built file with `fs.readFileSync` (built before `pulumi up` in CI), not from an env var. Routes:
   - `POST /github/login/oauth/access_token`: code exchange and refresh. It allows only listed client IDs and, if configured, adds the client secret on the server so it never reaches the bundle.
   - `POST /github/login/device/code`: optional.
   - `GET|POST /git/github.com/<owner>/<repo>.git/(info/refs|git-upload-pack|git-receive-pack)`: a streaming git proxy for isomorphic-git, forwarding the `Authorization` header.
   - `GET /healthz`.
   - Every route checks the `Origin` against `ALLOWED_ORIGINS`, including native origins such as `capacitor://localhost`, `https://localhost` and the Electrobun views scheme. The Worker stores nothing and logs no bodies or headers.
4. **CI**:
   - Fix `cloudflare-deploy.yaml`: pick npm or yarn consistently with the lockfile; build and test the Worker; `pulumi up` against the R2 backend; then a smoke check that `curl https://auth.nsheaps.dev/healthz` works and a disallowed origin gets 403.
   - Turn `cloudflare-preview.yaml` back on with the 1Password secrets step.
   - Add `typecheck` and Worker tests to the root check.
5. **The GitHub App can't be created with Pulumi.**
   - Add `cloudflare-apps/TASKS.md` (or a `github-apps/cept/README.md`) with the app's definition and the manual or manifest-script steps:
     - permissions: Contents read/write, Metadata read, optionally Pull requests and Issues
     - "Expire user authorization tokens" on
     - "Request user authorization during installation" on
     - callback URLs for `https://cept.nsheaps.dev/...`, `https://nsheaps.github.io/cept/...` and the native schemes
   - Store the client ID (public) in Pulumi config, and the client secret (if needed) in 1Password `Infrastructure/cept-github-app`.
   - Optionally manage installation-to-repo access in `github-org/` with `github:AppInstallationRepository`.
6. **Cept side** (in the cept repo, not iac):
   - Read `VITE_AUTH_RELAY` and `VITE_GIT_PROXY`, defaulting to `https://auth.nsheaps.dev`, plus `VITE_GITHUB_APP_CLIENT_ID`, from one config module.
   - Port github2's PKCE login and refresh into `@cept/core`.
   - Keep PAT login direct to api.github.com.
   - For space autodiscovery, call api.github.com directly (no relay): `GET /user/installations`, then `/user/installations/{id}/repositories` (or `/user/repos` with a PAT), then look for `space.cept.yaml` via the git trees or contents API.
