# Cept scope: in scope vs deferred

**Status:** Draft for owner confirmation, 2026-10-07 · **Owner:** nsheaps · **Source:** [requirements](requirements/README.md)

This page records what the current build-out covers and what is deferred. Nothing here is final until the owner answers the [open scope questions](#4-open-scope-questions). Once answered, the answers are recorded here and in the area files, and implementation starts in small PRs.

## Owner's scope statement

> Build Cept up to, but not including, live co-editing, CLI tools and daemons, the VS Code plugin, and databases. That means full space functionality, syncing with a remote on GitHub, comments, full Markdown file support with front matter for metadata, native app distribution bundles, the PWA, Pulumi setup for Cloudflare in nsheaps/iac for the GitHub App login (while also supporting PATs), and autodiscovery of spaces based on what the login has access to.

## 4. Open scope questions

Each question has a recommended default. If the owner accepts a default, the matching requirements move to §2 or §3.

### 4.1 Product questions

**Q1. Mobile in 'native app distribution bundles'.** Are the Capacitor iOS and Android apps in scope, or only the Electrobun desktop apps (Windows, macOS, Linux)?

- _Recommended default:_ Desktop (Win/macOS/Linux) and Android APK are in scope. iOS builds and runs in CI (simulator build) but distribution is deferred until an Apple Developer account is confirmed.

**Q2. Signing and store submission.** Do 'distribution bundles' mean signed, notarized builds and store submissions (App Store/TestFlight, Play Store, Mac App Store, winget, Homebrew cask), or downloadable artifacts on GitHub Releases?

- _Recommended default:_ Artifacts on GitHub Releases, signing wired but optional (unsigned with ::warning:: when secrets are absent, per REQ-APP-013). Store submissions are deferred. A Homebrew cask in nsheaps/homebrew-devsetup is a nice-to-have.

**Q3. Desktop formats and auto-update.** Which installer formats and architectures, and is auto-update in scope for this round?

- _Recommended default:_ macOS: dmg, arm64 + x64 (universal if Electrobun supports it). Windows: NSIS installer, x64. Linux: AppImage + deb, x64. Electrobun's built-in updater, fed from GitHub Releases, is in scope.

**Q4. Git hosts.** GitHub only, or any Git remote (GitLab, Gitea/Forgejo, generic HTTPS Git with a token)?

- _Recommended default:_ GitHub only (App + PAT). Read-only anonymous clone of any public HTTPS Git URL stays as it is today. Other hosts are deferred, but the AuthProvider interface stays host-agnostic.

**Q5. Other storage backends.** Are Google Drive, SFTP, Google sign-in, and S3/URL backends out of scope this round, given the owner listed only GitHub sync?

- _Recommended default:_ Out (deferred): REQ-WS-015, REQ-WS-016, REQ-AUTH-006, REQ-AUTH-007. In: browser IndexedDB, local folder in the desktop app (REQ-WS-009/010), File System Access API folders on web (REQ-WS-012), and Git/GitHub.

**Q6. Space functionality breadth.** Does 'full space functionality' include multiple spaces per repo (D-2), space create/rename/delete, the folder-as-tree layout with migration of existing flat spaces, and moving a space between backends (REQ-WS-020)?

- _Recommended default:_ In: multiple spaces per repo, the lifecycle (create, rename, remove-from-device, delete), the folder-tree layout plus migration, and .git detection (REQ-WS-021). Backend switching (REQ-WS-020) is limited to 'publish a local/browser space to a new GitHub repo'. Nested spaces stay deferred (D-3).

**Q7. Autodiscovery behaviour.** Which repos and branches does autodiscovery scan (default branch only? org repos? forks? archived?), and does it add discovered spaces automatically or list them for the user to pick?

- _Recommended default:_ Default branch only. All repos the credential reaches, including org installations. Forks and archived repos are skipped (archived ones can be shown read-only on request). Found spaces are listed under 'Discovered' and cloned only when opened or pinned.

**Q8. Branching and PRs.** Does GitHub sync include choosing a branch or making a new one, and opening PRs when a push to a protected branch is rejected?

- _Recommended default:_ Per-space branch selection is in. When a push is rejected, the fallback is 'push to a new branch'. Opening a PR from the app is deferred.

**Q9. Page history UI.** Is the Git-backed page history and diff view (REQ-NTN-016, HistoryViewer) in scope as part of GitHub sync?

- _Recommended default:_ In: per-page history list, diff, and restore for Git-backed spaces, with history fetched on demand.

**Q10. Notion-parity features beyond comments.** Which of these are in: page move/reorder (NTN-012), icon/cover pickers (NTN-013), templates UI (NTN-014), synced blocks (NTN-015), Notion import (NTN-017), @mentions (EDT-004)?

- _Recommended default:_ In: move/reorder (needs front-matter order), icon/cover (front-matter metadata), keeping the existing Notion ZIP import working (with databases imported as plain pages or CSV), and @page/@date mentions (needed for comment mentions). Deferred: templates UI, synced blocks, @person mentions.

**Q11. Links, backlinks, graph and search.** Are [[wiki-links]] (EDT-017), backlinks (EDT-021), the knowledge graph view (EDT-018 to 020), and full-text search over Git-backed spaces part of 'full markdown file support'?

- _Recommended default:_ In: relative Markdown links, [[wiki-links]], backlinks panel, and search across the active space (including Git-backed ones). Deferred: the graph view.

**Q12. Markdown extensions.** Do math, mermaid, footnotes, the fenced-annotation plugin registry, and the block-encoding decision (D-14: GFM, then fenced annotations, then data-type HTML; retire cept:block) count as 'full markdown file support'?

- _Recommended default:_ In: GFM incl. footnotes (EDT-014/015), math and mermaid as fenced annotations (EDT-010 to 012), and the one-pipeline and lossless round-trip work (D-14, D-15, EDT-005, 022 to 024). Deferred: the third-party plugin registry (EDT-013).

**Q13. Databases exclusion boundary.** Does excluding 'databases' also exclude inline/linked database blocks, the CSV-to-database Notion import path, and the existing unwired database UI components (hide vs remove)?

- _Recommended default:_ Exclude all of REQ-EDT-006 to 009 and D-16. Leave the existing library code untouched but remove database entries from the slash menu and UI so nothing half-working ships. Notion CSVs import as Markdown tables.

**Q14. Static rendering and publishing.** Is static site rendering and publishing (REQ-SSG, 'publish to web', the docs site built by Cept's SSG per D-12) in or out, given the CLI render command is out?

- _Recommended default:_ Out for this round, except the minimum to fix in-app bundled docs: generate them from docs/content at build time (REQ-WEB-018). The SSG and docs site are deferred with the CLI.

**Q15. Production origin and hosting.** Is the canonical app origin nsheaps.github.io/cept/app/ or a custom domain (cept.nsheaps.dev, already in ALLOWED_ORIGINS)? This decides OAuth callbacks, PWA scope and Worker origin checks (AUTH open question 10).

- _Recommended default:_ Keep GitHub Pages at nsheaps.github.io/cept/app/ for production. Register PR preview callbacks as well. Revisit the custom domain later.

**Q16. Worker code location and shape.** Where does the OAuth relay plus Git CORS proxy code live (nsheaps/cors-proxy, nsheaps/iac, or the cept monorepo), and is it one Worker or two?

- _Recommended default:_ One Worker, with source in the cept monorepo (packages/auth-relay, tested with Miniflare), built in CI and published as an artifact. nsheaps/iac Pulumi deploys it by version, along with the custom domain, secrets and ALLOWED_ORIGINS.

**Q17. GitHub App registration ownership.** Who owns the GitHub App (personal account nsheaps or an org), and is a manual registration plus a documented manifest acceptable, since Pulumi cannot create GitHub Apps?

- _Recommended default:_ An org-owned app ('Cept'), registered once from a checked-in app manifest. Client ID and any secret are stored as Pulumi config secrets in iac. Permissions: Contents read/write, Metadata read. User token expiration on.

**Q18. Offline and sync runtime in the PWA.** Do you approve D-4/D-5 as the sync model now that daemons are out (SharedWorker leader, falling back to a Web Locks leader tab; service worker for offline caching and queued flush only), and is full offline editing of GitHub-backed spaces with later push in scope?

- _Recommended default:_ Approve D-4/D-5 as stated. Full offline editing with queued commits and push-on-reconnect is in scope.

**Q19. Comment storage and notifications.** Sidecar file per page (<page>.comments.cept.yaml) or .cept/comments/<page-id>.yaml, and what notification level?

- _Recommended default:_ Sidecar per page, anchored by quote, so no edits to the Markdown. Bodies are Markdown. Notifications are only an in-app 'new since last visit' badge.

**Q20. Engineering prerequisites.** Are the enabling engineering requirements (REQ-ENG: mise tasks, exact pins, removing weakened CI gates per D-24, fixing red e2e gating releases, nx affected, secret scanning) implicitly in scope?

- _Recommended default:_ In, as prerequisites: fix CI red and gate weakening, mise tasks, and a secret scanner. Other REQ-ENG items only as needed.

**Q21. Open PR #67 and existing remote-space code.** Should open PR #67 (remote spaces with path ids, per-folder .cept.yaml, runtime docs clone) be finished, reworked into this plan, or closed?

- _Recommended default:_ Close or supersede it, salvaging the path-keyed ids and the README/index folder-page logic into the new space work. Per-folder .cept.yaml stays out (D-3).

## 6. nsheaps/iac: Pulumi and Cloudflare

### 6.1 What exists today

I looked through nsheaps/iac at /home/user/iac without changing anything. Pulumi is already set up there with two projects, and one of them (`cloudflare-apps`) is a Cloudflare stack written for Cept: it has a `cept.nsheaps.dev` DNS record, a Worker named `nsheaps-cors-proxy` whose allowed origins include Cept, and an `auth.nsheaps.dev` hostname. Nothing in that stack works yet:

1. **No working deploy.** Its only deploy run on 2026-03-05 failed (logs have expired, so the cause is unknown). Every manual step in `cloudflare-apps/TASKS.md` is still unchecked, and both preview workflows are switched off with `if: ${{ false }}`.
2. **The code is written for an older provider version.** `index.ts` uses the v5-style API, but `@pulumi/cloudflare` is pinned at ~6.21.0. I unpacked 6.21.0 and confirmed the mismatch:
   - `WorkersScript` now requires `scriptName` and takes `bindings: [{type: 'plain_text', ...}]`; `name`, `module` and `plainTextBindings` no longer exist.
   - `Zone` now needs `account: {id}` and `name`, not `zone`.
   - `cloudflare.Record` is deprecated in favour of `DnsRecord`.
   - So the stack most likely fails type-checking and `pulumi up` as written.
3. **The Worker only ever ships a placeholder.** Its code comes from the `CORS_PROXY_SCRIPT` env var, and CI never sets it, so every deploy uploads a stub that returns 503.
4. **`auth.nsheaps.dev` probably doesn't reach the Worker.** It is a CNAME to `nsheaps-cors-proxy.workers.dev`, but workers.dev hostnames include an account subdomain, so that target is likely wrong. There is no `WorkersCustomDomain` or `WorkersRoute` resource.
5. **CI installs with the wrong package manager.** CI runs `yarn --cwd cloudflare-apps install --immutable`, but that folder has a `package-lock.json` and no `yarn.lock`, and the root `package.json` declares no workspaces.
6. **Pulumi state isn't set up for CI.** CI sets neither `PULUMI_BACKEND_URL` nor `PULUMI_ACCESS_TOKEN`. The wrapper script falls back to local `file://` state, which wouldn't survive between CI runs. The plan to store state in R2 has a chicken-and-egg problem: the R2 state bucket is created by the same stack whose state would live in it.
7. **No GitHub token-exchange relay exists.** iac has no code for the GitHub login token exchange. The Worker's real code was meant to come from a separate repo, nsheaps/cors-proxy. This session can't reach that repo through the GitHub API (it returned 403), so its contents are unknown.

Cept's own spec already asks for this Worker. `docs/specs/requirements/09-remotes-and-auth.md` (REQ-AUTH-003/008/009) says one Worker provisioned through iac should handle the GitHub token exchange and refresh plus Git push/pull traffic, with an origin allowlist and no stored state. It lists most of these iac defects too, and it has 10 open questions (§"Conflicts and open questions"). Cept today has no login code wired into the UI; its GitHub provider talks to github.com directly (which browsers block) and the app hardcodes the public proxy `cors.isomorphic-git.org`.

The sibling project github2 has the closest existing example (`relay/relay.worker.js`, about 50 lines). It is a stateless, secret-free Worker that only accepts POSTs, forwards to a short allowlist of github.com login endpoints passed as `?url=`, and adds CORS headers (it allows any origin). The PKCE login code in `src/api/oauth.js` could be ported to Cept almost as-is. But github2's relay was never actually deployed: in production `src/config.js` sets `AUTH_RELAY = 'https://api.cors.lol/'`, a public third-party proxy that sees users' login codes and tokens. Its `PUBLIC_CLIENT_ID = '3946485'` also looks like an App ID rather than a client ID (those usually start with `Iv`), which is worth checking.

Recommendation: take github2's idea but don't copy the file. Build one hardened, shared, first-party Worker in iac and serve Cept from it (github2 and private-pages could move to it later). It should check origins, use fixed routes instead of an open `?url=` parameter, carry Git push/pull traffic, optionally add a client secret on the server side, and never log tokens.

The GitHub App itself can't be created with Pulumi; `github-org/README.md` says the same. It has to be registered by hand or with a manifest script. Pulumi can only manage which repos an installation can reach.

Finding the user's spaces doesn't need the relay. api.github.com sends CORS headers, so Cept can list installations and their repos directly (or the user's repos with a PAT), then check each repo for `space.cept.yaml`.

### 6.2 Cloudflare patterns in iac

Two Pulumi projects, set up the same way:

- **`github-org/`**: Pulumi YAML (`runtime: yaml`).
- **`cloudflare-apps/`**: TypeScript on Node (`runtime: nodejs`, `packagemanager: yarn`). Pulumi CLI 3.266.0 comes from mise; `@pulumi/pulumi` ~3.267.0 and `@pulumi/cloudflare` ~6.21.0 are pinned.
- **Stacks**: both have only a `prod` stack, with config in `Pulumi.prod.yaml`. The cloudflare-apps config is `workerName=nsheaps-cors-proxy`, `allowedOrigins` (`nsheaps.github.io`, `private-pages.nsheaps.dev`, `cept.nsheaps.dev`), `r2BucketName=nsheaps-pulumi-state` and `domainName=nsheaps.dev`. The Cloudflare account ID is read from config.

What `cloudflare-apps/index.ts` declares:

- an R2 bucket meant to hold Pulumi state
- the existing `nsheaps.dev` zone, to be imported
- proxied CNAMEs from `private-pages` and `cept` to `nsheaps.github.io`
- the `WorkersScript`, whose code comes from `process.env.CORS_PROXY_SCRIPT` or else a 503 stub
- `auth` as a CNAME to `<workerName>.workers.dev`

How it runs:

- **Locally**: `bin/pulumi-wrapper.sh [-C <dir>] <cmd>` runs `op run --env-file=<dir>/.env.op` (the file holds 1Password `op://` references) and picks the state backend: `PULUMI_BACKEND_URL` if set, then R2 if `AWS_*` keys and `PULUMI_R2_ENDPOINT` are set, otherwise local `file://.pulumi-state/`. The mise tasks `.mise/tasks/pulumi/{preview,up,refresh,destroy,stack-init}` call it, defaulting to `github-org`.
- **CI**:
  - `cloudflare-deploy.yaml` runs on pushes to main that touch `cloudflare-apps/**`. It loads `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and `PULUMI_CONFIG_PASSPHRASE` from 1Password vault `Infrastructure` using the repo secret `OP_SERVICE_TOKEN`, then does mise, `yarn install` and `pulumi/actions@v7 up --stack prod`. It sets no backend URL and no `CORS_PROXY_SCRIPT`.
  - `cloudflare-preview.yaml` is switched off with `if: ${{ false }}` and has no secrets step. `pulumi-deploy.yaml` and `pulumi-preview.yaml` do the same for github-org (preview also off).
  - The only cloudflare-deploy run and the matching pulumi-deploy run both failed on 2026-03-05; their logs have expired.
- **Manual steps**: setup lives in `cloudflare-apps/TASKS.md` (1Password items, zone import, R2 state migration, Pages custom domains, worker deploy), and every item is unchecked.
- **Other deploys in the repo**: Docker stacks go out through Arcane (`hosts/`, `arcane/`, `arcane-deploy.yaml`), not Pulumi. The root `yarn check` covers only Prettier and Docker Compose; it does not type-check `cloudflare-apps`.

Known defects:

- `index.ts` uses the v5 API against v6.21; I checked against the published package that `WorkersScript` now needs `scriptName` and `bindings`, `Zone` needs `account`/`name`, and `Record` is deprecated.
- The CNAME to workers.dev is the wrong way to point a hostname at a Worker.
- CI never injects the Worker code.
- The yarn/npm lockfile mismatch.
- There is no shared state backend for CI.

### 6.3 Existing GitHub App and OAuth infrastructure

**iac**

- No relay for the GitHub login token exchange exists, and the only Worker deploys a 503 stub.
- `cloudflare-apps/TASKS.md` mentions updating "GitHub OAuth App redirect URLs" for private-pages and cept, which suggests an OAuth App already exists somewhere for private-pages. It isn't in the repo.
- `github-org/Pulumi.yaml` manages repos, branch protection and teams. It has a commented-out `github:AppInstallationRepository` for the automation app, and its README notes that GitHub Apps themselves can't be managed by Pulumi.
- The org's other app, automation-nsheaps (actor 2549081), is used for CI and repo settings only, not for user login.
- The real Worker code was meant to come from nsheaps/cors-proxy, which this session can't reach through the GitHub API (403), so its contents are unknown.

**github2 precedent** (`relay/relay.worker.js`, `src/api/oauth.js`, `docs/specs/auth.md`, skills `auth-relay` and `pkce-login`)

- The relay is a stateless Cloudflare Worker deployed by hand with `wrangler deploy`.
- It holds no secrets and only accepts POSTs.
- The target comes from a `?url=` parameter and must be one of `github.com/login/oauth/access_token` or `github.com/login/device/code`.
- It sends `Access-Control-Allow-Origin: *`.
- The client side handles login (PKCE S256 with Web Crypto, `state` in sessionStorage, redirect to `/callback`), refresh using the refresh_token, and device flow, all through the relay. A PAT login and an "app private key in the browser" login go straight to api.github.com.

Problems with it as precedent:

- github2's production config points `AUTH_RELAY` at the public third-party proxy `https://api.cors.lol/`, so a third party sees login codes and tokens.
- `PUBLIC_CLIENT_ID = '3946485'` looks like an App ID rather than a client ID (client IDs usually start with `Iv`).
- Its spec assumes GitHub's "SPA client" preview (github/roadmap #1153) allows a secret-free, CORS-enabled token exchange. That is unverified and may not apply to every app, so the relay may need to add `client_secret` itself.

**Can Cept reuse it?**

- Reuse the client-side PKCE and refresh logic (port it to TypeScript in `@cept/core`, using its own `TokenStore`) and the relay idea.
- Don't reuse the Worker file as-is. It allows any origin, has no git push/pull proxy, has no optional server-side secret, and has no tests or IaC.
- Build one shared, hardened first-party Worker in iac instead. github2 and private-pages could later move onto it, which would also get github2 off cors.lol.

**Cept today**

- `packages/core/src/auth/github.ts` is an OAuth-App-style provider that POSTs straight to github.com (blocked by CORS in a browser) and can send `clientSecret`.
- It has no PKCE, and no UI uses it.
- `App.tsx` hardcodes `cors.isomorphic-git.org`.
- `docs/specs/requirements/09-remotes-and-auth.md` REQ-AUTH-002/003/008/009/015/016 already specify the target design.

### 6.4 Proposed layout for Cept login

Keep the existing TypeScript project `cloudflare-apps/` (it already owns `cept.nsheaps.dev` and the Worker with Cept's allowed origins). Fix it and add a proper relay.

1. **Bootstrap / state.** Either move the R2 state bucket into a tiny `cloudflare-bootstrap/` project that uses local state checked in encrypted or kept in 1Password, or use Pulumi Cloud. Then set `PULUMI_BACKEND_URL` to R2 in every workflow and `.env.op`, so CI has durable state.
2. **Port `index.ts` to the v6 API** and split it into modules:
   - `cloudflare-apps/src/dns.ts`: `Zone` (`account`, `name`) and `DnsRecord` for `cept` and `private-pages`.
   - `cloudflare-apps/src/oauth-relay.ts`: a `ComponentResource` named `OAuthRelay`:
     - a `WorkersScript` with `scriptName`, ESM code and `mainModule`, and `bindings` for `plain_text` `ALLOWED_ORIGINS`, `ALLOWED_CLIENT_IDS` and `GIT_ALLOWED_HOSTS=github.com`, plus optional `secret_text` `GITHUB_CLIENT_SECRET_<id>` from `pulumi config --secret` or 1Password
     - a `WorkersCustomDomain` for `hostname auth.nsheaps.dev`, replacing the broken CNAME, or a dedicated `cept-auth.nsheaps.dev`
     - outputs: relay URL and client ID
3. **Worker source lives in iac** at `cloudflare-apps/workers/oauth-relay/`: `src/index.ts`, vitest unit tests with miniflare/workerd, and an esbuild bundle. Pulumi reads the built file with `fs.readFileSync` (built before `pulumi up` in CI), not from an env var. Routes:
   - `POST /github/login/oauth/access_token`: code exchange and refresh. It allows only listed client IDs and, if configured, adds the client secret on the server so it never reaches the bundle.
   - `POST /github/login/device/code`: optional.
   - `GET|POST /git/github.com/<owner>/<repo>.git/(info/refs|git-upload-pack|git-receive-pack)`: a streaming git proxy for isomorphic-git, forwarding the `Authorization` header.
   - `GET /healthz`.
   - Every route checks the `Origin` against `ALLOWED_ORIGINS`, including native origins such as `capacitor://localhost`, `https://localhost` and the Electrobun views scheme. The Worker stores nothing and logs no bodies or headers.
4. **CI**:
   - Fix `cloudflare-deploy.yaml`: pick npm or yarn consistently with the lockfile; build and test the Worker; `pulumi up` against the R2 backend; then a smoke check that `curl https://auth.nsheaps.dev/healthz` works and a disallowed origin gets 403.
   - Turn `cloudflare-preview.yaml` back on with the 1Password secrets step.
   - Add `typecheck` and Worker tests to the root check.
5. **The GitHub App can't be created with Pulumi.**
   - Add `cloudflare-apps/TASKS.md` (or a `github-apps/cept/README.md`) with the app's definition and the manual or manifest-script steps:
     - permissions: Contents read/write, Metadata read, optionally Pull requests and Issues
     - "Expire user authorization tokens" on
     - "Request user authorization during installation" on
     - callback URLs for `https://cept.nsheaps.dev/...`, `https://nsheaps.github.io/cept/...` and the native schemes
   - Store the client ID (public) in Pulumi config, and the client secret (if needed) in 1Password `Infrastructure/cept-github-app`.
   - Optionally manage installation-to-repo access in `github-org/` with `github:AppInstallationRepository`.
6. **Cept side** (in the cept repo, not iac):
   - Read `VITE_AUTH_RELAY` and `VITE_GIT_PROXY`, defaulting to `https://auth.nsheaps.dev`, plus `VITE_GITHUB_APP_CLIENT_ID`, from one config module.
   - Port github2's PKCE login and refresh into `@cept/core`.
   - Keep PAT login direct to api.github.com.
   - For space autodiscovery, call api.github.com directly (no relay): `GET /user/installations`, then `/user/installations/{id}/repositories` (or `/user/repos` with a PAT), then look for `space.cept.yaml` via the git trees or contents API.
